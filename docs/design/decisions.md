## Design — Key Decisions & Trade-offs

### 决策 1：优先用 Context Engineering，但允许少量 deterministic 展示层兜底
**问题**：是否应该完全依赖 AI 通过 GeoGebra DSL 自己把图画“干净”？例如隐藏角度数值标签、隐藏坐标轴等。

**结论**：采用“Prompt 优先 + 展示层兜底”的混合策略。

**理由**：
- **模型不稳定性**：不同 provider/温度/上下文长度会导致同一需求偶发遗漏（例如忘记 `SetLabelVisible(false)`）。
- **展示卫生属于“最后一公里”**：隐藏轴/网格、隐藏角度数值标签这类规则，属于**UI 观感一致性**，并不改变数学内容。
- **避免无限 prompt 复杂度**：把每个展示小细节都塞进 prompt，往往会牺牲鲁棒性与可维护性。

**约束**（避免“封装一切”的滑坡）：
- deterministic 规则只允许作用于：
  - **画布级别**（axes/grid 等）
  - **标签/样式级别**（关键点 label、角度数值 label 等）
  - **失败清理与安全**（rollback、dialog 消费）
- deterministic 规则不得“替 AI 做数学内容选择”，例如自动添加证明线、自动选择定理步骤。

### 决策 2：几何题默认隐藏坐标系
**结论**：对“纯几何证明/性质题”应用几何预设：隐藏坐标轴/网格；对代数题/解析几何显示或按需显示。

**原因**：坐标系对儿童/初学者是噪音；证明图强调关系而非坐标数值。

**开放问题**：解析几何（带坐标证明）属于混合类，需 spec 中定义“何时展示坐标系”的判定规则。

### 决策 3：失败必须无残留（Rollback First）
**结论**：任何一次执行尝试失败，都应当回滚本次新增对象，再进入下一次修复重试。

**原因**：叠图会迅速摧毁可读性；而且会污染下一次修复时的对象列表，使 AI 更难修复。

### 决策 4：Auto 模式内部优先 Kimi（并保留降级）
**结论**：Auto 模式的 provider 选择顺序以 Kimi 为首选，后续按可用性降级；同时保留关键场景本地兜底。

**原因**：
- 外部 provider 受鉴权/限流/偶发失败影响，必须有“可用性策略”
- 教学场景里，稳定可用比“偶尔更聪明”更重要

**开放问题**：UI 默认值应该显示 Auto（内部 Kimi-first）还是直接默认选中 Kimi？这属于产品层决策。

### 决策 5：画布感知统一走 tool runner（多轮 HTTP），不默认直传 state
**问题**：当 LLM 需要画布信息/前端能力时，如何“通用且可扩展”地完成工具调用？

**结论**：采用 **tool runner 主链路**：服务端返回 `kind=tool_request`，前端执行工具并回传 `TOOL_RESULT`，再继续到 `kind=final`。

**理由**：
- **稳定性优先**：不依赖长连接（SSE/WS），失败可重试、可观测。
- **可扩展**：前端能力（读取画布/更新 UI）可持续以 tool 形式扩容，不引入新的专用 API。
- **成本控制**：默认不发送 `canvasState`，只在模型明确需要时才通过 `get_canvas_state()` 获取。

**约束**：
- 暂不考虑并发，但协议设计不应锁死未来并发。
- 不新增“为某个题型/模型”的硬编码分支；优先用工具/提示/契约解决。
