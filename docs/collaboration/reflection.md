# Reflection 工作流（LLM 失败复盘）

## 角色与触发
- **发起人**：wei（PM）。在看到 LLM 失败/用户体验问题时创建一条 reflection 任务（创建 bd issue，并指派 assignee）。
- **执行人**：一个或多个 agent（按 bd issue 的 `assignee` 分配）。每个任务至少由一人负责。

## 输入
- 最近的错误日志条目（见 `logs/llm-errors.log`）。
- 失败场景的用户提示、系统 prompt 版本（promptVersion）、错误命令/反馈。

## 步骤（最小可行）
1) **收集**：从 `logs/llm-errors.log` 抽取相关条目，确认发生频次与时间范围。
2) **诊断**：判断根因属于：
   - Prompt/上下文设计缺陷（例：提示建议使用我们环境不支持的命令）。
   - 工具/bridge 层不兼容（例：JS API 期望参数范围不同）。
   - 模型选择/降级策略问题。
3) **泛化修正**：提出能覆盖同类错误的修改（避免只 patch 单条命令），优先顺序：
   - 更新提示词/constraints/commandbook。
   - 必要时调整执行层兜底（如参数归一、命令替换）。
4) **实施**：提交修改（提示词/代码），并在 PR 中引用反射任务 ID。
5) **验证**：
   - 补充/更新 `docs/self-test.md` 的相关用例。
   - 本地或 dev 环境跑至少一次针对性自测（含修复前场景）。
6) **记录**：在 `docs/collaboration/decision-log.md` 如涉及规范/约束变更则追加决策；关闭 bd issue（`bd close`）并写明验证结果。

## 输出
- 修正后的提示词/代码。
- 新增或更新的自测用例与运行结果。
- bd issue 状态更新（status/notes）。

## 校验循环（举一反三）
1) **模式泛化**：对每个发现的问题，列出 2–3 个“同类变体”问题（措辞不同、约束稍变、点/边/角位置变），作为新增自测。
2) **A/B 验证**：在修复后跑这些变体，记录通过/失败；若部分失败，说明修复不够泛化，继续迭代。
3) **可接受标准**：短期可接受 = 同类变体通过率 ≥ 80%，且无严重误导；中期目标 = 95%+ 或有执行层兜底。达标后才关闭任务。
4) **失败复盘**：对仍失败的变体，补充“为什么当前方案不适用/不可接受”的说明，并提出下一轮可选方案（提示增强、执行兜底、减少自动假设等），形成下一个 reflection 子任务。
5) **循环终止条件**：达到可接受标准，或 PM（wei）确认暂缓继续提升；否则重复 1–4。
